# The world atlas web app

The app lives in `Anatolia/atlas` (Next 15, React 19, three.js, React Three Fiber). Paths below are relative to that folder unless they start with `src/`, `scripts/` or `tests/`. How to run it is in [`Anatolia/atlas/README.md`](../Anatolia/atlas/README.md). How to publish it, and what a hosted copy cannot do, is in [`deploy.md`](deploy.md). The data it reads is described in [`world-catalogue.md`](world-catalogue.md) and [`suitability-model.md`](suitability-model.md).

## Four views and one coordinator

`app/page.tsx` renders `components/WorldCoordinator.tsx`. The coordinator owns which view is showing, the crossfade between views, and the address bar. Nothing else writes the URL, apart from the model layer's one parameter.

| View | Component | What it is |
| --- | --- | --- |
| `globe` | `components/globe/GlobeExplorer.tsx` | The world globe, its sites, and its chrome. |
| `atlas` | `components/AtlasApp.tsx` | The Anatolia terrain atlas. Its state lives in the hooks under `components/atlas/`. |
| `place` | `components/place/PlaceView.tsx` | A standalone terrain close-up of one published site. |
| `walk` | `components/walk/WalkView.tsx` | A walk through one site listed in `lib/walk/walkSites.ts`: its model, or the Gaussian splat built from photographs. |

Each view owns a WebGL canvas, so each is loaded with `next/dynamic` and mounted only while it is on screen. A transition gives the new view a fresh key, fades the old one out for 620 ms, then unmounts it. One canvas is alive afterwards. Each view is wrapped in `components/scene/SceneGuard.tsx`: if WebGL will not start, or the view throws while drawing, the failure stays in that view and the notice offers a way back (and Try again, when that is a different action). It does not replace the whole page.

Handoffs:

- **Globe to atlas.** `lib/globe/handoff.ts`. Inside the Turkey bounds (25.5–45°E, 35.8–42.2°N) the globe offers the atlas below 900 km and enters it when a zoom crosses 450 km. A link that opens low over Turkey does not bounce straight in. "Open in Anatolia atlas" on a site card enters with that site's id, which is a world-catalogue id. The atlas (`components/atlas/useInitialSite.ts`) opens a curated site of that id, else a place of its own catalogue with that id, else the curated site the catalogue record stands for: the record is read from its detail shard and matched by name and nearness with the matching the renown ranking uses (`lib/atlas/curatedMatch.ts`), so the card of Göbekli Tepe (`Q214944`) arrives on the curated `gobekli-tepe` with its panel and "Walk the site". An id that is none of these selects nothing: from a card the map still opens centred on that place.
- **Atlas to globe.** The Globe button, or zooming well past the overview (`components/atlas/useGlobeExit.ts`). The globe reopens at 1,500 km, above the offer line.
- **To a place and back.** "View terrain" on a site card. Leaving returns to the view you came from, and on the globe the card of that site reopens.
- **Atlas to a walk and back.** `lib/atlas/walkHandoff.ts`, `components/atlas/useWalkEntry.ts`. Only for the sites in `lib/walk/walkSites.ts`. "Walk the site" on the site panel enters. So does zooming: with the camera looking within 800 m of the site, the atlas offers the walk below a camera distance of 3,000 m and enters it when a zoom crosses 700 m. A camera that starts below 700 m does not bounce straight in, flights do not count, and the zoom entry is off while the trip replay is open. On the way in the atlas camera pushes at the site and the fading layer swells (`.diving` in `WorldCoordinator.module.css`); neither happens under `prefers-reduced-motion`. `useWalkEntry` fetches the walk's code as soon as the atlas has a walkable site, so the dive does not land on an empty screen. The walk's exit button is labelled "Anatolia map": it returns to the atlas with that site selected, at the usual site distance, which is above the offer line. The atlas is mounted afresh, so it does not come back at the exact camera the visitor left.
- **Globe to a walk and back.** `lib/globe/walkHandoff.ts`. A walk site may name `globeCardIds`, the world-catalogue ids of the globe site cards that offer it. Giza names the pyramid complex (`Q12508`, which is also the walk's own id) and the Great Pyramid (`Q37200`). Those cards carry "Walk the site", which enters through the coordinator with the plain crossfade; the globe has no zoom entry to a walk. The exit follows the site, not the route taken: a site with globe cards returns to the globe ("← Globe") with the card the visitor came from open, or the first of its cards when the walk was opened by its address, and every other site returns to the Anatolia map (`walkReturn`). The globe is mounted afresh at the look it last had, or at its default look when the walk was opened by its address. Back from the walk lands on the globe entry, which names the open card, and Back after "← Globe" returns to the walk.

## URL scheme

`lib/globe/viewUrl.ts` parses and writes it. Within a view the coordinator uses `history.replaceState`, so the back button is not filled with camera moves, selections or the walk's source. A change of view (globe, atlas, place, walk) is the one thing that adds a history entry (`historyEntryForView` in `lib/globe/viewHistory.ts`, written by `components/useViewHistory.ts`), so Back returns to the view before and never leaves the app from inside it. On `popstate` the coordinator reads the address it has landed on and mounts that view without adding an entry. The view is mounted afresh, as on any transition: Back from a walk opens the atlas on the site named in its entry, at the usual site distance, so it does not fall straight back into the walk, and Forward enters the walk without the camera dive. The exit buttons add an entry like any other change of view, so Back after "← Anatolia map" returns to the walk. While the globe moves, the URL is written at most every 400 ms.

| Address | Meaning |
| --- | --- |
| `?view=globe&lon=38.00&lat=30.00&alt=13000` | The point at the centre of the screen, to 2 decimals, and the camera altitude in whole kilometres. Altitude is clamped to 100–40,000 km. |
| `…&site=<id>` on a globe address | The site whose card is open. |
| `…&model=<layerId>` on a globe address | The recording-pattern layer that is switched on (`components/globe/model/modelUrl.ts`). |
| `…&theory=<id>` on a globe address | The theory the lens is on: the Theories panel opens on that theory and the sites it is about are ringed. The id must be a slug (`THEORY_ID_PATTERN`) of a theory in the registry; any other value is dropped, and the next write of the address leaves it out. `/?view=globe&theory=<id>` is the link another page uses to open the lens. |
| `…&tour=<id>&stop=<site id>` on a globe address | A guided tour, and the stop it is on. `tour` is `wonders` or `tas-tepeler`. `stop` is one of that tour's catalogue ids; a missing stop opens the first. An unknown tour is dropped, and a stop that is not on the tour is dropped. Other views ignore both. No address carries a coordinate: the stop is the site's id. |
| `?view=atlas` or `?view=atlas&site=<id>` | The Anatolia atlas, optionally opened on a site. The atlas writes the id of the selected place here, curated or catalogue, and removes it when the selection is cleared, so a reload opens the same place. A world-catalogue id that stands for a curated site is corrected to the curated id once that site is selected; an id that selects nothing is removed. |
| `?view=place&site=<id>` | The close-up of one site. |
| `?view=walk&site=<id>` | The walk through one site, opening on its model when it has one. An id with no walk opens the atlas instead, and the address is corrected to `?view=atlas&site=<id>`. The id of a globe card that offers a walk (`Q37200`) opens that walk, and the address is corrected to the walk's own id (`Q12508`). |
| `?view=walk&site=<id>&source=photographs` | The same walk opening on the splat from photographs. The model is the default and is never written; any other value is read as the default, and the coordinator rewrites a walk's address as it opens, so `&source=bogus` does not stay in it. A site with a model and no photographs (Giza) opens on its model whatever `source` says, and the parameter is dropped. |
| `/site/<slug>` | One published catalogue site, opened on the globe with its card. The slug is the site's name plus its catalogue id, for example `/site/gobekli-tepe--q214944`. A bare id (`/site/q214944`) redirects to that slug. An id the catalogue does not hold is not a page, so a candidate or an unpublished place has none. While that card stays open the address stays on this path and does not gain camera coordinates. Choosing another site, closing the card, or changing view returns to the `?view=` form. `?site=` links are unchanged. |

No parameters means the globe at its default look (38°E, 30°N, 13,000 km) with a slow idle turn. A site id must match `^(?:Q\d+|[a-z0-9]+(?:-[a-z0-9]+)*)$`. Anything else is dropped. No address ever carries a site's coordinates: a link names a published id. A share page's title, description and preview image name the site and do not draw or print a location.

The globe's top bar, the Anatolia map, the place view and the walk each have **Share**. On a site card it copies `/site/<slug>`. On a view it copies the address of that view, or the pretty path when that is what is open, and leaves out `&model=` when that value is a recording-pattern layer. A phone with a share sheet uses it; a desktop copies the link and says so.

## The globe scene

`components/globe/GlobeView.tsx` owns the canvas. `GlobeSurface.tsx` draws the Earth with `3d-tiles-renderer`: a generated WGS84 ellipsoid with XYZ imagery draped on it, and `GlobeControls` for orbit, zoom and tilt.

**Frame.** The scene is Earth-centred Earth-fixed, in metres, and the tiles group is not rotated. So scene coordinates are ECEF coordinates:

- +X leaves the Earth at 0°E 0°N
- +Y at 90°E 0°N
- **+Z at the north pole.** "Up" is +Z, not three's usual +Y.

Use `lonLatHeightToScene(lon, lat, height)` and `sceneToLonLatHeight` from `lib/globe/ellipsoid.ts`. They take degrees. Do not write your own conversion.

Things that catch people out:

- The canvas uses a **logarithmic depth buffer** (near 10 km, far 10⁹ m). A custom `ShaderMaterial` needs the `logdepthbuf` shader chunks or it will z-fight or vanish.
- `GlobeControls` raycasts the tiles only, so points and atmosphere shells never become the drag pivot. Give a new mesh a no-op `raycast`.
- Draw order is set by `renderOrder`: ice and sea level 2, model overlay 3, haze 4, glow 5, site points 6 and above.
- The camera cannot come closer than 60 km. Detail belongs to the place view.
- `GlobeView` reports the look (centre point and altitude) about 8 times a second. Keep it in a ref unless the component really must re-render.

**Imagery.** `lib/globe/basemaps.ts` lists the basemaps. The first is the default. If its host does not answer a probe, the second is used. Tiles are streamed and never stored. The Base map section of the settings panel offers every entry; until the visitor picks one, the default and its fallback apply. The choice is kept in `useGlobeExplorer`, and `GlobeExplorer` hands the entry to `GlobeView`. The attribution line under the globe comes from the same entry.

## How sites are loaded and drawn

Loading (`lib/world/catalogueLoader.ts`, `lib/world/cellLoader.ts`, `components/globe/useSiteLayers.ts`):

1. At start: `index.json`, `core.json` (40,000 sites) and `featured.json`. The Anatolia atlas reads the same three only to rank its curated sites, so when it is opened directly it asks for them 2.5 s after its own data has loaded (`useWorldCatalogue(deferMs)`): a slow `core.json` then cannot hold up the map or a browser check that waits for the network to go quiet. The atlas's own catalogue, `wikidata/sites.geojson` (3.8 MB), is asked for at once but nothing waits on it: the map is ready without it and the dots appear when it lands. The dev server does not gzip (`compress` in `next.config.ts` is on only in production), because it gzips each response as it is asked for, which measured 5 to 20 times slower than sending these files plain over loopback. A busy dev server is still slow with every file, and slowest with the largest.
2. Below 2,500 km of altitude: the 10° cells in view, nearest first, at most 40 at a time. A cell is fetched once. The cache keeps 48 cells and forgets the least recently wanted.
3. When the OpenStreetMap layer is switched on: `osm-megaliths.json`, once.
4. When the search box is first focused: `names.json`, so search covers the sites whose cells are not loaded.
5. When a card opens: one `detail/<bucket>.json` shard.

Drawing (`lib/globe/siteBlock.ts`, `components/globe/GlobeSitePoints.tsx`, `sitePointsMaterial.ts`): each block of columns becomes typed arrays and **one `THREE.Points` draw call**. The shader hides the far side of the globe, sizes a point by how well known the site is, and fades from a soft glow in orbit to solid dots close up. Colour comes from the site type (`lib/world/siteTypeStyle.ts`). The filter does not rebuild geometry. It writes a per-point "shown" attribute (`lib/world/siteFilter.ts`).

On top of the points: featured markers with serif names (`GlobeFeaturedMarkers.tsx`, label placement in `lib/globe/labelLayout.ts`), count badges where points crowd (`GlobeClusterBadges.tsx`, one-degree buckets from `lib/globe/siteGrid.ts`), and a ring on the selected site. A site with a report from the last 90 days (`NEWS_RECENCY_DAYS` in `lib/news/recentNews.ts`) also wears a quieter ring (`GlobeNewsRings.tsx`). It starts on. The legend and the Layers section of the settings panel share the switch. The ring follows the same filters as the dots, so an undated site stays unmarked while undated sites are off. Only a world-catalogue id is marked: a curated Anatolia id is not a second pin, an OpenStreetMap id is not marked, and a candidate cannot be, because it is not in the catalogue. A site that is not in `core.json` is marked only when its detail record exists, and only while the filters would keep an undated site, since that file does not hold its dates. The list of those sites sits in the legend and flies to each one; the legend starts closed on a narrow screen, and nothing opens a card on its own. The pulse is CSS and stops under `prefers-reduced-motion`, leaving the ring still.

### Sites on the Anatolia terrain map

The terrain map draws its sites in the globe's style, from the globe's own pieces.

- **Colour means period here**, not site type. `lib/periodStyle.ts` maps the four periods onto the globe's colour families (`SITE_PALETTE` in `lib/world/siteTypeStyle.ts`). The legend, the layer switches and the occupation bar read the same file.
- **The catalogue** (`components/CatalogueMarkers.tsx`, `components/atlas/cataloguePoints.ts`): every published place is its own dot in one `THREE.Points` draw call, with the globe's dot fragment shader. A dot takes the colour of the earliest period its record names, or pale gold when it names none. Undated places are smaller and fainter, and fainter still from the overview (half strength, easing back close up), so the dated periods carry the colour. There are no count badges: where places crowd, the dots do. From the country overview a dot is a soft 5.5 px mote with no rim, so density reads as a glow; it hardens into a rimmed dot by halfway in and grows to 12 px close up (`tuneCataloguePointsMaterial`). On a screen narrower than 1,000 px the overview fits the country into fewer pixels, so dots and curated pins shrink with it, to no less than 0.55 of their size (`markerScale`); the shrink eases off as the camera comes close.
- **Picking** is a custom `raycast` on the points: the place nearest the pointer ray within 9 screen pixels. A click opens that place.
- **Curated sites** (`components/atlas/SitePinMarkers.tsx`, placed by `SitePins` in `components/AtlasScene.tsx`, texture in `components/atlas/sitePinTexture.ts`): a bright core in a halo of the period colour, with a dark rim and soft shadow so it holds on pale terrain. A bright hollow ring is an approximate location. A filled pin also throws a soft additive glow of its colour on the map (`sitePinGlowTexture`), as the globe's featured markers do; it is faint enough that a cluster adds up to its colour and not to white, and an approximate ring has none. A pin is 28 px wide at the overview and 34 px close up. Where pins crowd at the overview, the best known stand and a pin within 30 px of a better-known one stands back (`lib/atlas/pinDeclutter.ts`): it fades out over 0.35 s, in one step under `prefers-reduced-motion`, and while it is out it has no name and cannot be hovered or clicked. The distance shrinks as the camera comes in and every pin stands from about 400 km of camera distance inwards. The selected site always stands, and search reaches every site at any zoom.
- **Curated names are always on**, in the globe's serif label class and laid out by the globe's `placeLabels` (`components/atlas/useSitePinLabels.ts`, about 8 times a second). A name goes right of its pin, else left, else centred above, else below (`AROUND_MARKER` in `lib/globe/labelLayout.ts`; the globe still uses right and left only), else is left out until the pin is hovered. It never covers another name, a named pin, or the chrome over the map. The best-known sites are named first, with the selected site ahead of them. `lib/atlas/curatedRenown.ts` reads that order from the world catalogue (`components/atlas/useCuratedRenown.ts`): the catalogue's featured monuments come first, then the Wikidata sitelink count (`importance` in `core.json`). A catalogue record counts for a curated site when it shares one of its names and lies within 0.3°. Names are compared without case or diacritics, and a catalogue title that holds several names ("Tarsus/Antiochia ad Cydnum") counts under each. A site with no such record, or only records with no sitelinks, takes the best record within 0.3° whose name begins with one of its names ("Göreme National Park" for Göreme, "Hacılar Mound" for Hacılar). A site that still has nothing keeps the order of `public/sites.geojson`, as every site does until the catalogue has loaded; today those are Ravendel, Birecik, Marash, Tarsus, Adana, the Saleph crossing and Bodrum Castle. The ranking only reads the catalogue: it moves and adds nothing. The country overview names up to 14 sites, kept apart; every site in view is named close up. The "Place names" setting only adds names to catalogue dots.
- **The terrain** darkens its pale tones in the surface shader (`lib/shade.ts`) without changing their hue: sand turns bronze, grey relief stays grey, dark imagery is left as it is. So the map sits in the dark chrome and the dots can glow on it. The place view shares the shader. The night theme multiplies the graded colour by a cool half-light (red 0.5, green 0.58, blue 0.72), after the grade so the grade cannot lift it back; dots and pins keep their brightness, so they glow more at night. On the national map the same shader draws a thin pale line where land meets water, and fades the outer 8% of the terrain block into the background (`mapEdge` in `components/NationalTerrain.tsx`), so its straight eastern and southern edges do not read as a cut.
- **The regional block** (Şanlıurfa at 120 m) fades into the national map over the outer fifth of its width (`REGION_FEATHER` in `components/AtlasScene.tsx`). On the default base map its raster is the elevation tint blended with satellite imagery, which is greyer and darker than the national tint; `lib/sceneRasters.ts` gives the colour gains that bring its average back to that tint (`regionalGain`, the `albedoGain` uniform). Other base maps need none.
- **The window of a selected site** (about 6 km of 15 m terrain) fades into the map over the outer fifth of its width (`DETAIL_FEATHER`). On the default base map its Sentinel true-colour image is a contrast stretch, blue-grey with near-black shadows, so it is drawn with warm gains and a tenth of plain sand mixed in (`detailGrade` from `lib/sceneRasters.ts`). Those gains were set for Göbekli Tepe, so a darker window (Sayburç, Nevalı Çori, Harran) is first lifted towards that window's average brightness: the scene measures the loaded image and `windowLiftExponent` in `lib/windowLift.ts` gives an exponent for it. An exponent, not a gain, because every window is already stretched to white and a gain would burn out its light ground. It never darkens an image and stops at a limit, so a truly dark one is not turned grey. The grade is for looks only: the swipe comparison, the satellite base map and every other layer show the image as it is.
- **The selected place**, curated or catalogue, wears the globe's ring (`.ring` in `components/globe/GlobeSites.module.css`). Its pulse is CSS and stops under `prefers-reduced-motion`. The name of a selected curated site stands 27 px from the pin, clear of the ring (`--label-gap` on the label).

## Picking

`components/globe/useGlobePicking.ts`. There is no GPU picking and no raycast against the points.

1. The pointer ray is intersected with the ellipsoid (`intersectRayWithEllipsoid`).
2. A pixel tolerance (9 px for a mouse, 20 px for touch) is turned into degrees on the ground at that distance.
3. The one-degree bucket grid of each drawn block returns the nearest shown site within that reach. A featured site wins over an ordinary neighbour unless that one is much closer.

A press and release within 5 px is a click. A drag is not. Hover runs at most every 50 ms and feeds the tooltip.

Known limit: the tolerance is measured on the ground, so it shrinks towards the limb where the surface is foreshortened.

## The globe chrome

`components/globe/useGlobeExplorer.ts` is the view model: catalogue, filters (`useSiteFilter.ts`), selection (`useSiteSelection.ts`), the wonder tour (`useWonderTour.ts`), and which panel is open. `components/globe/chrome/ExplorerChrome.tsx` lays out the DOM over the canvas and is memoised, so camera movement does not re-render it. The overlay layer ignores the pointer. Controls opt back in.

**Guided tours.** `lib/world/guidedTours.ts` names the routes and `lib/world/wonders.ts` still holds the wonders route's order. Taş Tepeler visits published Şanlıurfa sites the world catalogue already holds. Each stop has a short caption written here and the source it was taken from. The same flight that opens a site card moves the camera; a stop that is not in the core file is read from its cell or its detail record. Nothing plays by itself. Choosing another site, or closing the card, ends the tour. The bar (`TourBar`) shows the caption. Its close control is the shared close button, and Escape ends the tour before the site card, because the tour sits in front of that card on the dismiss stack. Stops the catalogue leaves undated stay drawn while the tour is running; the undated switch and every other undated site are unchanged. The Wonders panel starts either route (`data-action="start-tour"`, `data-action="start-tas-tepeler-tour"`). On the Şanlıurfa view, Taş Tepeler (`data-action="tas-tepeler-tour"`) opens the globe on that tour. A link is `?view=globe&tour=tas-tepeler&stop=<id>`. On a narrow screen the bar wraps under its title and the card below it scrolls. Hooks: `[data-role="tour-bar"]` with `data-tour` and `data-stop`, `[data-action="tour-previous"]`, `[data-action="tour-next"]` and `[data-action="tour-end"]`.

On a screen up to 640px wide the same chrome draws in, so the globe stays the main thing. The title shortens to "Atlas" (the accessible name stays "Atlas of early monuments") and the search box is an icon until it is focused. The legend is a chip of the count of sites shown; the key and the site-records sentence open from it. The timeline is a chip of the current range (`describeSpan`, so "All time" or "Before 9000 BCE") that opens upward, and its era chips and named-period chips scroll sideways. One line along the bottom stays in view: the imagery host and its licence, then each catalogue's short credit (`lib/globe/compactCredits.ts`; Wikidata CC0, Pleiades CC BY 3.0), then the full imagery sentence, which scrolls. The OpenStreetMap megalith credit stays its own line while that layer is on. A notch or a home indicator is kept clear (`viewport-fit=cover`, and `env(safe-area-inset-*)` on the chrome). Wider screens are unchanged. The Anatolia map, on the same width, keeps its tools on one row and folds its year bar into a chip of the range (`aria-controls` the bar). Its key scrolls sideways. A published site card (`.panel.place-guide`) is capped at 46dvh or 420px, whichever is smaller, with padding for a home indicator. While the globe's legend is open, the catalogue names stay in that card and drop off the footer line, so they are not printed twice. The footer's phone wording for the Anatolia map names the licences (EOX CC BY-NC-SA 4.0, GEM-15 CC BY 4.0, Pleiades CC BY 3.0, Copernicus).

**Closing a layer.** The same close button (`components/chrome/CloseButton.tsx`) sits at the top right of every panel, sheet, legend and results list that can be dismissed: an X, a 44px target, the accessible name "Close" plus the layer's name, and the ochre focus ring. A chip that opens a layer stays (the globe legend, the phone time-range sheet, the Anatolia key, year bar and period dock). Escape closes only the frontmost open layer (`lib/chrome/dismissStack.ts`): a search list, then the shortcut list, then a side panel, place card, chart, landscape note or trip bar, then a legend, key, period dock or phone sheet. The walk's disclosures are separate. They still close with Escape once the pointer is free.

**The timeline and its named periods.** `chrome/GlobeTimeline.tsx` holds a two-thumb year slider (`YearRangeSlider.tsx`), six date-band chips that mean the same everywhere (`lib/world/worldEras.ts`), and under them a row of named-period chips (`components/NamedPeriodChips.tsx`). Period names start at different dates in different places, so `lib/world/namedPeriods.ts` is a small table in which each period has a region, a span and a source: a coarse box for Anatolia and one for Egypt, and two periods shown everywhere (the Younger Dryas and the Late Bronze Age collapse, which is an eastern Mediterranean event). The regional chips show when the centre of the view is inside the region's box from below 6,000 km. Pressing a chip sets the year range to that period, pressing it again returns to all time, and its tooltip gives the dates, how they were read and the source. `GlobeExplorer` turns each look report into a region key and passes the chrome a new list only when the key changes, so the memoised chrome does not re-render as the camera moves. The Younger Dryas is also drawn as a labelled band on the slider's track (`components/TimelineIntervalBand.tsx`). The Anatolia map's year bar (`components/TimelineControl.tsx`) carries the same band and the Anatolia and worldwide chips under its track, always, since that map is Anatolia at every zoom; its four broad colour periods stay in the Periods dock. The sources are registered in `docs/data-sources.md`.

**Play history.** "Play history" (`data-action="play-history"`) on the globe timeline, and the same control on the Anatolia year bar, sweeps a playhead from the start of the chosen range to its end. A site appears when its dates overlap the growing window, and stays; the type filter and Include undated are left as the visitor set them. Undated sites start hidden (`DEFAULT_SHOW_UNDATED`). Pause, 1x, 2x and 4x sit beside the button, and the playhead (`data-role="history-playhead"`) can be dragged. While a sweep is going, the readout is the year and its date band (on the Anatolia map, the broad period that contains the year), and the closed phone chip shows the year. The playhead moves on a short timer. The site filter is told only when the year crosses a 100-year step, and the globe rewrites the existing per-point shown attribute instead of building the geometry again. Under `prefers-reduced-motion` the playhead jumps about one date band at a time and does not glide. On a phone the controls are in the timeline sheet. While the sweep is running, the ice layer follows the playhead year rather than the middle of the range. Hooks: `data-playing`, `data-play-speed`, `data-play-year` on the timeline, and `[data-action='play-speed']`.

**The settings panel.** One panel, the same in every view: `components/settings/SettingsPanel.tsx`. It shows a row of presets and then six sections in a fixed order, Layers, Timeline, Base map, Theme, Labels and Walk (`lib/settings/settingsSections.ts`). It is presentational and holds no state: each view passes in the controls it has for a section, built on its own existing state, and a section a view has nothing for shows one line saying where that setting applies ("Walk options apply inside a site walk."). Each view opens it from a control labelled Settings:

- On the globe the Settings button of the top bar opens `chrome/GlobeSettingsPanel.tsx`, an `ExplorerPanel` on `PanelShell`. It took the place of the Layers panel and its button. Its Layers section holds that panel's switches, the In the news switch (the same one the legend holds), the site type filter (the same `SiteTypeFilter` the legend holds, on the same state) and the recording-pattern controls. Timeline is the date-band chips, the named periods of the region in view and the undated switch (`GlobeTimelineSetting.tsx`); the year slider stays under the globe. ### The ice and sea level layer

A context layer for date-based questions: where a model puts the ice sheets and the land above today's sea at a past date. `components/globe/paleo/`, off by default, switched on under "Context layer" in the Layers section of the settings panel.

- **Data.** `public/paleo/` holds one 1440×720 class raster per step, every 500 years from 20,000 BCE to the present (45 files, about 1 MB together), and `index.json` with each step's year and the source's credit. The rasters use the recording-pattern layer's grid and its rule for values: 0 is sea, 1 is land where the sea is today, 2 is ice, 20 is other land, and only 1 and 2 are drawn. They are built from CHELSA-TraCE21k (CC0 1.0, see `docs/data-sources.md`) by `scripts/fetch_paleo_context.py` and `scripts/build_paleo_context.py`; the pure part is `src/ai_archaeology/paleo_context.py`.
- **Drawing.** `GlobePaleoOverlay.tsx` draws one ellipsoid shell with the recording-pattern layer's class-raster material (`createModelOverlayMaterial`), two of its ten colours set to the layer's two tones. Like that layer it tests the surface by front-face culling and neither reads nor writes the depth buffer, samples the raster without filtering, ignores raycasts, and fades out as the camera comes low enough for a cell to pass for detail. A change of step swaps one texture; nothing runs over the data per frame. It is rendered by `GlobeExplorer` beside `sceneLayers`, not through that prop, because its step follows the timeline, whose state lives in `useGlobeExplorer`.
- **Which year.** `usePaleoLayer.ts` and `lib/world/paleoIndex.ts`. The layer shows the step nearest the middle of the years picked on the timeline (`paleoYearForSpan`, `nearestPaleoStep`), so the Younger Dryas chip shows 10,500 BCE. While Play history is running it follows the playhead year instead. With the timeline on all time it is at the present day and draws nothing. The timeline starts at 12,000 BCE, so the panel also has a "Time step" list that picks any step by hand, back to the Last Glacial Maximum; "Follow the timeline" hands it back.
- **What the visitor is told.** The panel shows a statement whether the layer is on or off, the step, a legend, how the year is picked, and the source with its licence. A label over the globe (`PaleoChip.tsx`, top left, under the recording-pattern layer's label when both are on) says the same in short for as long as the layer shows. All of the wording is in `paleoWording.ts`.
- **Hooks.** `[data-role='globe-explorer']` carries `data-paleo` (`off`, `loading`, or the step's year). In the panel: `[data-role='paleo-slot']`, `[data-role='paleo-enabled']`, `[data-role='paleo-statement']`, `select[data-role='paleo-step']` (`timeline` or a year), `[data-role='paleo-readout']` with `data-year`, `[data-role='paleo-legend']`, `[data-role='paleo-credit']`. Over the globe: `[data-role='paleo-chip']` with `data-year` and `data-too-close`.
- It is not in the address and not in any preset: the "Deep past" preset sets only the timeline and filters, and the layer then follows that range once it is switched on.

Limits. Say these whenever the layer is described:

- **It is one model, not a record.** The ice is the ICE-6G_C reconstruction (Peltier and others 2015) as CHELSA-TraCE21k interpolated it between that model's 500-year steps, with glacier outlines from two glacier databases. Other reconstructions draw the margins differently.
- **It is not a coastline.** The source lowers one global sea level over present-day sea-floor depths. It leaves out the sinking of land under ice and its rise afterwards, sediment laid down since, and tectonics. A cell is about 28 km wide. The layer cannot say whether a given site stood on a shore.
- **It gives no sea level figure.** The layer shows where the source model has land that is sea today. The source publishes no sea level for its steps, and the atlas does not state one of its own: a figure read back from the files would be the atlas's number with no source behind it.
- **Ice is drawn only where it stands at least 150 m above today's surface.** The source's ice-surface field has values far beyond the ice (over most of Scandinavia at the present day), so it cannot be used as a mask alone. The build therefore also asks for the step's surface to stand 150 m above today's. Ice that is as thick today (Greenland, Antarctica, mountain glaciers) and the thin edge of an ice sheet are not drawn, and at the present day nothing is.
- **Nothing north of 84°N,** where the source has no data, and each cell is the nearest pixel of the source's 8 arc-minute overview, not an average.

## The place view

`components/place/PlaceView.tsx` takes `{ siteId, onExit }`.

- `lib/place/placeSite.ts` finds the site's name, type, dates and credit from the catalogue files. An id of a curated Anatolia site (`?view=place&site=ephesus`), which the close-up API also resolves, is named from `public/sites.geojson` with its period; no control in the app links to such an address, only a typed one reaches it.
- `lib/place/placeTerrain.ts` asks the close-up API for `meta`, which triggers the build, then for `height`. It gives up after 135 s. `lib/place/placeFailure.ts` turns the API's status into what the view says: on a server that builds no close-ups (503) it says so at once and offers no "Try again".
- `components/place/PlaceScene.tsx` builds the terrain mesh with a skirt, drapes the satellite image or the hillshade, and lights it with a movable low sun. Geometry helpers are pure functions in `lib/place/placeGeometry.ts`.

The scene here is a local Web Mercator block, not ECEF. Heights are scaled by `1 / cos(latitude)` to match the Mercator stretch.

## The walk view

`?view=walk&site=<id>` (`components/walk/`) is the coordinator's fourth view, entered from the Anatolia atlas or, for Giza, from a globe site card. It shows one site with a visitor inside it, who can walk on the floor or fly above it. A site has a Gaussian splat built from photographs, and may also have a modelled reconstruction, which then opens first. Giza has a model only.

- `lib/walk/walkSites.ts` lists the sites, and for each the splat file, eye height, walk radius, alignment and an optional `modelId`. A site may be `modelOnly`: no splat is looked for and no choice of Model or Photographs is shown. It may name `globeCardIds` (see the handoffs above). An id that is not listed has no walk: the coordinator opens the atlas instead.
- Keys: click to look around (pointer lock, Esc frees it), W A S D to move, Shift to move faster, the left and right arrows to turn and Page Up and Page Down to look up and down (neither needs the pointer lock, so a visitor without a mouse can look around; the up and down arrows move like W and S), F to switch between walking and flying, E and Q to rise and sink while flying, R to return to the start, walking, whatever the mode was. `lib/walk/walkKeys.ts` holds the layout. Space is left alone because it would press the focused button.
- `lib/walk/walkMovement.ts` is the pure movement maths: the velocity eases towards what the keys ask for, so starts and stops are smooth at any frame rate. The keys turn the view the same way (`lookStep`: about 90° a second, eased, and a view at rest is left to the mouse). A walker stays at eye height inside the walk radius. In a model a walker also collides (`lib/walk/walkObstacles.ts`, handed to the limits as `walkerStep`): each frame they are pushed out of any obstacle they entered by the shortest way, which slides them along it, and ground more than 0.7 m above their feet stops them, 0.3 m short where it rises more than 1.4 m (a face near eye height). So a rock face blocks, and benches and drawn steps are climbed through `groundHeightM`, which counts the top of every rock mass and of `laidGround`. Any drop is allowed. `lib/walk/modelObstacles.ts` derives the obstacles once from the model: a pillar's shaft is a box, a round pillar a circle, and a ring wall a chain of straight pieces that leaves the gap and every `openings` stretch free, about 250 footprints at Göbekli Tepe and under 100 at Karahan Tepe, never the stones. A flyer passes through everything, the photographs have no collision, and R and the "Show me" buttons place the walker directly. A flyer stays inside a dome of three times that radius, between 0.4 m and a ceiling of twice the radius, capped at 40 m. Leaving fly mode eases down to eye height, and a walker who lands outside the walk radius can walk in but not further out. The ground is flat at y = 0 unless the limits are given a `groundHeightM(x, z)` lookup: then the walker's eyes ease to eye height above the ground under them, a flyer stays 0.4 m above it, and `startPosition` puts the start and the R key on it.
- `components/walk/WalkControls.tsx` applies it each frame and reports pointer lock. The wheel climbs only over the scene: the listener is on the canvas's own element, which also receives every wheel event while the pointer is locked, so scrolling a panel, the footer or a button never takes off. It is also behind a gate (`wheelGateAfter` in `walkMovement.ts`): no wheel event counts until the scene has been drawn for 1.5 s, and the first to count must follow 1 s without one, both counted in drawn frames with a long frame counting as 0.25 s (while the page is stalled the browser holds wheel events back, which by the clock would look like a pause), so a zoom on the atlas that carries on into the walk, slow notch by notch or as a trackpad's inertia, leaves the visitor walking; once open the gate stays open. The footer and a showing landmark card take pointer events for the same reason. `WalkerHandle.standAt` lets the chrome stand the walker at a viewpoint (see the hypothesis panel). Only elements marked by `pointerLockTrigger.ts` (the scene and the entry prompt) lock the pointer, so the buttons stay clickable.
- `components/walk/WalkView.tsx` owns the state (`WalkView({ site, initialSource, onSourceChange, onExit })`) and `WalkChrome.tsx` is the chrome. Its colours and type are the `--globe-*` tokens of `app/theme.css`; it uses no backdrop blur, because that would be redrawn over a moving canvas every frame. The pieces:
  - Top left: the exit (a button when `onExit` is given, labelled "← Anatolia map" or "← Globe" after the view that holds the site, and a link to `/` otherwise), the site name, and a note while the splat loads.
  - `WalkHud.tsx` holds `LookPrompt`, the entry prompt, and `ModeButton`. The prompt is a small chip low in the middle, the same shape as the atlas's walk offer, so the view stays in sight: "Click to look around", the line "W A S D to move · arrows to turn · scroll down to fly", and one tip (gold rings give information in a model; the photographs are sharpest at the pale rings). It stays hidden until the scene has drawn a frame (`ShownSignal.tsx`), and while the pointer is locked. Once the visitor has pressed a movement key or taken off it is `data-compact="true"`: only "Click to look around", on one line at the foot of the screen (above the footer below 1,200 px), so it does not cover the names over the markers while flying and the way to lock the pointer stays in sight. It is the same element throughout, because the controls bind to it once.
  - The right-hand column (`.side`) runs top to bottom: `WalkSourceToggle.tsx` (Model, Photographs, for a site with a model) beside the mode button and, in the photographs, `ViewpointStepper.tsx` ("Sharp viewpoints" between two arrow buttons, see below), then three disclosures, `WalkKeyLegend.tsx` ("Keys", the full legend, and in the photographs the sentence about where the splat is sharp: at the pale rings, fading out away from them), the hypothesis panel and `WalkSettings.tsx` ("Settings", the settings panel described under the globe chrome), then the landmark card at the foot. Being one column, they cannot cover one another: when it is short the disclosures scroll. The disclosures share a `name`, so opening one closes the others.
  - `WalkFootnote.tsx` is the footer, bottom left. One line always shows and says what is on screen: "A schematic model from published dimensions, not a survey." or "A reconstruction from visitors' photographs, not a survey.", plus the hypothesis sentence while any layer is on. "Limits and sources" opens the model's full note and sources, or the photographs' caveat and the link to the credits file, which opens in a new tab and lists only the photographs the splat was trained on.
  - Escape closes any open disclosure once the pointer is free.
  - The choice of Model or Photographs is reported through `onSourceChange`; the coordinator writes it to the address (`&source=photographs`) and hands it back as `initialSource`, so a reload or a copied link opens the same one.
  - Below 1,200 px wide the prompt is centred in the space left of the column and hides while the footer is open; a click on the scene still starts the look. Below 700 px the prompt is not shown and the footer takes the bottom edge.
- Hooks for browser checks on `[data-view='walk']`: `data-walk-source` (`model`, `photographs`), `data-walk-state` (`checking`, `ready`, `missing`, `unavailable`; `unavailable` while the photographs or the scene have failed; always `ready` for a model that is drawing), `data-walk-failure` (that failure's kind, `webgl`, `memory`, `file` or `unknown`, or empty), `data-walk-shown`, `data-walk-mode` (`walk`, `fly`), `data-walk-locked`, `data-walk-landmark` (the id of the landmark whose card shows, or empty), `data-walk-hypotheses` (the ids of the conjectural layers that are on, space separated), `data-walk-viewpoint` (the number, from 1, of the sharp viewpoint last jumped to in the photographs, or empty). Also `[data-action='walk-exit']`, `[data-role='walk-prompt']`, `[data-role='walk-keys']`, `[data-role='walk-settings']`, `[data-role='walk-footnote']`, `[data-role='walk-mode']`, `[data-role='walk-source']` with a `[data-source]` button for each choice, `[data-role='walk-landmark']`, on a card with open questions `[data-role='walk-landmark-tabs']` with `data-walk-landmark-tab` (`about`, `questions`) and a `[role='tab'][data-tab]` button for each, `[data-role='walk-theory']` with `data-theory` and `[data-action='walk-theory-back']` while a theory is open, and `[data-role='walk-hypotheses']` with an `input[data-layer]` for each layer and, for a layer with a viewpoint, a `[data-action='layer-show'][data-layer]` button. In the photographs, `[data-role='walk-viewpoints']` holds `[data-action='viewpoint-previous']` and `[data-action='viewpoint-next']`.
- Landmarks. `lib/walk/landmarks.ts` is the pure part: a landmark is an id, a name, an enclosure, an optional pillar number, two to four sentences and a source. Its text is kept apart from where it stands, because each source has its own positions. A landmark of a rock-cut model names a `placeId` instead, a key of that model's `landmarkPlaces`. A placed landmark either `surrounds` the walker (a building) or is a thing to face. `nearestLandmark` picks the card: the nearest landmark in range (4.5 m for a pillar, the inner radius for an enclosure), a pillar only when roughly faced or within 1.5 m. Every distance is measured on the floor (x and z), with height only a loose gate of 12 m, because in the photographs the visitor is on a walkway 5 to 8 m above the pillars and in the Karahan model on a terrace above the rooms; so a walker over a pillar gets its card without facing it, and any such pillar before the enclosure it stands in. The card on screen is passed back in and holds on 0.6 m past its range, until the walker has turned side-on to it, and until another landmark is 0.6 m nearer, so a card does not flicker at an edge. `LandmarkWatcher.tsx` runs it each frame, `LandmarkCard.tsx` shows the result in an `aria-live` region without needing a click, and `LandmarkMarkers.tsx` floats a still gold ring above each landmark, with its name while flying. Names that would cover one another on screen are thinned (`lib/walk/markerNames.ts`, `useUnclutteredNames.ts`): the marker nearest the camera keeps its name and the rest show theirs once the view pulls them apart. Every ring always shows.
- What we don't know. A landmark that an open question names (`questionsForLandmark(site id, landmark id)` in `lib/theories/theoryRegistry.ts`, see [`theories.md`](theories.md)) gets two tabs on its card, "About" and "What we don't know"; a landmark with none shows its text with no tab row. The landmark ids are the same in the model and the photographs, so both show them. `LandmarkTabs.tsx` is the tab row (`lib/walk/landmarkTabs.ts` holds the tabs and the key rule): one tab is in the Tab order, the left and right arrows, Home and End move between the two, and while the focus is on a tab those arrows do not turn the walker. With the pointer locked a tab cannot be clicked, like the rest of the chrome, but Tab still reaches it. `LandmarkQuestions.tsx` lists the questions with `QuestionList`; choosing a theory puts its `TheoryCard` in place of the list, inside the card, with a "← Questions" button, and Escape goes back once the pointer is free. The focus moves to that button and back to the theory's button. The card then takes what is left of the column and scrolls, so it still covers nothing. Each card opens on "About": the body is keyed by landmark. The questions side is not read out by the live region, because the visitor opened it. Its styles are in `LandmarkCard.module.css`; the card's own paragraph style is scoped to `.landmarkAbout` so it does not restyle the theory record.
- A site's landmarks live in one file (`lib/walk/gobekliTepeLandmarks.ts`, `lib/walk/karahanTepeLandmarks.ts`) registered in `lib/walk/walkLandmarks.ts`. In the model a landmark stands at the pillar or enclosure it names. In the photographs it stands where the file's `PHOTOGRAPHS_POSITIONS_M` table says, keyed by landmark id, in walk metres after the splat alignment; a landmark with no row there is not shown. Never guess a row. The Göbekli Tepe splat's walk radius is 36 m so that every row can be reached on foot.
- `components/walk/WalkScene.tsx` draws the splat with drei's `<Splat>`, which reads the 32-byte `.splat` format and already turns y-down capture data upright. Its props stay at their defaults: `alphaTest` and `alphaHash` both turn on depth writing, which cuts hard edges into splats that are meant to blend. `SiteSplat.tsx` wraps it for one reason: drei keeps each file's data for the life of the page together with the renderer that first loaded it, and reads that renderer for every later `<Splat>` of the file, but the walk's canvas is rebuilt on every change of source and every re-entry, so without help the second visit to Photographs showed the backdrop and no splat. `SiteSplat` remembers each file's first renderer and points the four members drei reads from it (`properties`, `getContext`, `getCurrentViewport`, `resetState`) at the renderer now drawing; check it again when drei is upgraded. One sort worker and the parsed arrays of each file stay alive until the page is reloaded: that is drei's cache, bounded at one per site. `SplatBackdrop.tsx` is what shows where no photograph looked: a sphere with a plain dusk gradient and a paler horizon, so a flyer who has turned away from the site can still tell which way is level; it draws nothing of the site. The stage also darkens a little toward the edge of the screen (`.stage::after` in the photographs only). The canvas pixel ratio adapts (`useAdaptivePixelRatio`, drei's `PerformanceMonitor`): at most 1.5 at first, 2 while the frame rate holds, 1 when it does not, and after 12 steps it stays where it is.
- Sharp viewpoints. A splat is sharp only from where its photographs were taken. `lib/walk/gobekliTepeViewpoints.ts` and `karahanTepeViewpoints.ts` list those camera positions in walk metres with a point each camera looked at, thinned so that cameras within 1.5 m looking within 30° of each other are one viewpoint (26 from 41 photographs at Göbekli Tepe, 8 from 17 at Karahan Tepe). They are written by `scripts/splat/export_viewpoints.py` from the COLMAP model and the site's alignment, registered in `lib/walk/walkViewpoints.ts`, and must be exported again after a retrain or a change of alignment. They are camera positions in the walk's own frame, not finds and not map coordinates. `lib/walk/photoViewpoints.ts` is the pure part. Three things use them:
  - The fade. `useSplatFade.ts` (used by `SiteSplat.tsx`) draws the splat in full while the camera is within 6 m of a viewpoint, measured in all three directions, and eases it out to nothing at 22 m, where only `SplatBackdrop` is left; both distances are chosen by eye (`SHARP_WITHIN_M`, `GONE_BEYOND_M`). It is one opacity for the whole splat, a uniform added to one line of drei's fragment shader, set each frame from the nearest of the few dozen viewpoints; it is not a fade of each splat by its own evidence, and nothing loops over the splats. Thin streaks go first, because stacked splats of solid stone stay opaque for longer. The cost is the view from high above: at the fly ceiling the photographs are gone, and the markers and landmark rings are what is left to steer by. A site with no table is drawn in full. If a drei upgrade rewords that shader line the fade silently stops.
  - The markers. `ViewpointMarkers.tsx` lays a small still pale ring on the ground under each viewpoint, smaller than a landmark's gold ring and without its bead. They do not fade.

Without it the view away from the site is a wall of pale streaks. With it the far side of the shelter roof is gone too.

To add a site's model, write its layout file, add the id to `WalkModelId` and a row to `walkModels.ts`.
- The layout numbers only the pillars that carry a landmark. A ring names them by slot (`numberedSlots`, counted clockwise from the gap) and a central pair by `pillarNumbers` (west, then east); `findPillar` looks one up. Published: Pillar 31 is Enclosure D's western and Pillar 18 its eastern central pillar, and Pillar 43 stands on the north-west beside a gap in the northern wall (Schmidt 2010). Estimated and marked `[EST]`: the slots of Pillars 33 and 27, and which of Pillars 9 and 10, and of 1 and 2, stands east. Rings are evenly spaced, so even a published side is only the nearest slot.
- `components/walk/ModelScene.tsx` draws the model with the same `WalkControls`. `EnclosureStones.tsx` draws about 6,000 blocks as one instanced mesh for each kind of stone (`InstancedBlocks.tsx`): rough wall stones in uneven courses and of uneven lengths, large slabs laid or set up on their own, pillar blocks that taper to the foot, plain dressed blocks, the limbs of the relief, and roof timbers. Laid and dressed stone is `grained`: `stoneGrain.ts` adds weathering and a fine grain in the shader from world metres, so a face in shade is not one flat tone and nothing tiles, and darkens the foot of whatever stands on the floor (22% at the floor, gone 0.55 m up), where little of the sky reaches. Every kind except the wall stones has worn edges: `lib/walk/blockBevel.ts` is a unit block of 44 triangles (a plain box has 12) with a strip along each edge, and `wornEdges.ts` pulls its vertices in by a width in metres in the vertex shader (4.5 cm on a slab, 3.5 cm on a pillar, 2.5 cm on dressed stone, never more than 0.3 of the thinnest side), so one geometry serves blocks of every size and the strip is shaded from one face to the next like a rounded edge. The wall stones, which are nearly all of the blocks, stay plain boxes, and the shadow pass draws every block as a plain box. Their edges are rounded in the light instead (`addShadedArrises` in `wornEdges.ts`): within 3.5 cm of an edge the fragment shader turns the normal toward the neighbouring face and darkens the joint a little, from the stone's own size and place, with no more triangles and no noise lookup, and the effect fades out before it is finer than a pixel. Presentation only: the sizes are still the layout's. Each stone's inner face runs from joint to joint a little out of line and a little turned, inside the band the layout gives the wall, and where two stones of a course meet one stands proud of the other by at least 1.4 cm on each face and 6 mm on top (`courseStones` in `enclosureModel.ts`), so no two faces nearly agree and cross inside the 4 cm overlap. `lib/walk/pillarRelief.ts` sketches the published arms, hands, belt and loincloth of Enclosure D's central pair as raised bars: each arm is two tapered bars, upper arm and forearm, that narrow from shoulder to wrist and meet in a corner at the elbow, and each hand is five thin fingers on the narrow front; no animal relief is drawn, and the cards describe those instead. `EnclosureFloors.tsx` is a pale disc inside each ring, in the mottled `BedrockMaterial.tsx`. `ModelBackdrop.tsx` puts both models in one evening: `eveningLight.ts` holds every number of it in one place. The key is a warm low sun with the only shadow map. It reaches 128 m from the start across the light and along it; seen down the low ray that ground is a flat rectangle, so the map is one too (4096 px across, about 6 cm of ground to a texel). Nothing in a model moves, so the map is drawn once and again only when a layer is switched (`shadowCastersKey`), not on every frame. Three shadowless fills stand in for the sky: a hemisphere light (pale and cool from above, the warm sand of the sunlit earth from below; a browner one turns the underside of every pillar head to rust), the bright sky around the sun, and the blue sky opposite it, so limestone in shade stays pale and a little warm instead of turning to grey concrete, and still shows which way each face looks. Haze starts 45 m out. Change the mood there, not by tinting a material. `ModelSky.tsx` is the sky dome (deep blue overhead, dusk along the horizon, gold toward the sun, a soft sun disc with no edge to its glow) and the far hills, which pale into the haze toward their foot and take a little of the sunset under the sun; `ModelFloor.tsx` is the ground, a fine grit tile under broad patches of shader noise that never repeat. Nothing is downloaded.

- What the Karahan model draws. AD: a circle 23 m across whose western half is a 4.3 m rock face at the edge of the terrace and whose eastern half is a free-standing dry-stone wall on ground level with its floor, a two-step bench 1.24 m high (smooth rock on the west, laid stones on the east), 16 T-pillars and the central pair, standing although both were found collapsed. No entrance is drawn, since none is published. AB: a rock-cut room 6 by 7 m, drawn 2.3 m deep, with four taller and six shorter round bedrock pillars, the flat slab, a ledge on the west wall with the carved head jutting from its upper front as a plain rounded form with no face, turned a little to the south, on a short neck of rock that broadens into the wall, the 0.7 m porthole as a real round hole bored through the rock between AB and AD with five steps below it inside AB, four exit steps in the north-east corner, and the serpentine channel as a dark line on the rock. AA: 7 by 8.5 m and 1.1 m deep, north of AB and a little west, with its 6.6 m bench and two steps. AC: a low kerb, upright stones on the north and rock on the south, under a cap of flat stones, because its interior was not excavated. `components/walk/RockCutSite.tsx` draws it: `BedrockTerrace.tsx` is the rock as one extruded solid with the rooms as holes (weathered top, paler cut faces), a floor patch in each room and every rock mass, each with its upper rim worn round (12 cm on the terrace and the rooms, 4 cm on benches and steps, chosen by eye); `RockCarvings.tsx` is the round pillars, the head and its neck, and the wall of the porthole, shaded darker toward its middle; laid and dressed stones go through `EnclosureStones.tsx`. Everything cut from the bedrock shares `BedrockMaterial.tsx`: one limestone colour under low-contrast weathering, level beds, two sizes of grain and fine pitting, computed in the shader from world metres with five noise lookups, so floors, faces, benches and pillars read as one rock, nothing tiles, and the grain stays sharp at arm's length (each size of grain fades out before it is finer than a pixel). Rock far below the surface is a little darker, and with `footM` the foot of a bench, step or round pillar is darker where it meets its floor, by the same amount as a standing stone's. The cut faces of the terrace do the same: the wall of a sunken room is darker at that room's floor (`wallFootings` in `rockCutModel.ts` gives the shader each room's bounds and floor), and every other cut face at the low ground. The same material leaves out the fragments inside a bore, which is how the porthole is open without cutting the solid. The edge of the terrace is a smooth curve through the estimated points.

## The puzzles page

`/puzzles` (`app/puzzles/page.tsx`) is a plain document rendered on the server, outside the coordinator and with no WebGL. It lists the standing questions of `docs/theories.md` grouped by site. Under each question are the facts it rests on, each with its kind and source; the theories that try to explain it, each with its status and a link to `/?view=globe&theory=<theoryId>`; and beside them every `experiment` evidence entry those theories list, marked with the theory it supports or goes against. A question with no theory reads "Not known. No theory is recorded yet." The grouping is `puzzlesBySite` in `lib/theories/puzzlesIndex.ts`, which also holds the site names, so a new site needs a name there. The page applies the saved light or dark theme, links back to `/`, and is reached from the About panel. It holds no locations.

## The close-up API

`GET /api/closeup?id=<id>&part=<part>[&terrain=copernicus]` (`app/api/closeup/route.ts`, `lib/closeupCache.ts`, `lib/closeupCatalog.ts`).

| `part` | Returns |
| --- | --- |
| `meta` (default) | JSON: `bounds` (EPSG:3857 west, south, east, north), `width`, `height`, `pixelSizeM` (Mercator), `groundPixelSizeM`, `elevation` (`min`, `max`), `attribution` (`relief`, `satellite`). |
| `height` | `width × height` unsigned 16-bit values, scaled between `elevation.min` and `elevation.max`. Decode with `decodeHeight` in `lib/terrain.ts`. |
| `hillshade` | JPEG, light from 315° at 45°. |
| `satellite` | JPEG, EOX Sentinel-2 cloudless 2020. |

Rules and limits:

- **The request carries a published id, never coordinates.** A request with `lon` or `lat` is refused with 400. The id is resolved to a point from the Anatolia site files, then from `public/world/detail/<bucket>.json`.
- An unknown id, or a site beyond **80° north or south**, is 404. Web Mercator stretches without bound towards the poles.
- A window that would cross the **180° meridian** is refused by the worker and comes back as 502.
- The window is **10 km across on the ground**. Relief is the GEM-15 surface model at 15 m, so about 667 pixels a side. Where GEM-15 has no data (Russia, China, Mongolia, Greenland, and south of 61°S) the worker falls back to Copernicus GLO-30. `terrain=copernicus` asks for GLO-30 directly.
- The server builds a window by running `scripts/closeup_window.py` with the repository virtualenv's Python, or `ATLAS_PYTHON`. The worker reads open elevation tiles over the network. It is stopped after 120 s. A first build takes roughly 10 to 15 s.
- One build per id, shared by all callers. At most 2 builds at once (`ATLAS_CLOSEUP_CONCURRENCY`).
- Results are cached in a private temporary directory, or `ATLAS_CLOSEUP_DIR`. The cache is capped at 64 MB (`ATLAS_CLOSEUP_MAX_BYTES`), and the least recently used sites are evicted. Nothing is written into the repository.
- A server without the repository's Python cannot build a window. `closeupsAvailable` in `lib/closeupCache.ts` decides: `ATLAS_CLOSEUPS=on` or `off`, and when that is unset, off on Vercel (which sets `VERCEL`) and on elsewhere. When off, the answer is 503 with the body `close-up-unavailable`, given after the id is validated and before any catalogue file is read. [`deploy.md`](deploy.md) has what the app shows then.
- Only a 200 is cached by the browser (an hour); every other answer is `no-store`.
- Other failures are 502 with the body `close-up-failed`. The detail goes to the server log.

It shows a surface model at 15 m. It can show a tell, a terrace or a large enclosure in its landscape. It cannot show a wall.

## Where to add things

**A new site type.**

1. Append it to `SITE_TYPES` in `src/ai_archaeology/world/records.py`. `index.json` carries the list, so the web files stay self-describing.
2. Teach the ingesters to assign it: `SITE_TYPE_RULES` in `wikidata_world.py` and in `pleiades_world.py`. First match wins, so order matters.
3. Give it a title and colour in `lib/world/siteTypeStyle.ts`. Without one it is drawn as "Other sites".
4. If the model should count it, add it to a class in `src/ai_archaeology/suitability/labels.py`.
5. Rebuild the catalogue and run the tests.

**A new basemap.** Record its licence in `docs/data-sources.md` first. Add an entry to `GLOBE_BASEMAPS` in `lib/globe/basemaps.ts` with its XYZ template, maximum level, licence and attribution. The first two entries are the default and its fallback. Every entry is offered in the Base map section of the settings panel, with its title and licence.

**A new panel.** Add its name to `ExplorerPanel` in `useGlobeExplorer.ts`, a button to `PANEL_BUTTONS` in `chrome/ExplorerTopbar.tsx`, and a branch in the side slot of `chrome/ExplorerChrome.tsx`. Build it on `chrome/PanelShell.tsx`. Keep its styles in a CSS module next to it.

**A new setting.** Keep its state where the view keeps the rest (`useGlobeExplorer`, the hooks under `components/atlas/`, `WalkView`) and pass its control into the matching section of `SettingsPanel` from that view's wrapper: `chrome/GlobeSettingsPanel.tsx`, `components/SettingsMenu.tsx` or `components/walk/WalkSettings.tsx`. Do not add a section for one view: the six in `lib/settings/settingsSections.ts` are the same everywhere, and a new one needs its line for the views without it. A new preset goes in `lib/settings/settingsPresets.ts`, with the state it sets in each view that can apply it and a case in `check_settings.mts`; it may only set state that already exists.

**A new layer on the globe.** Pass it through the `sceneLayers` prop of `GlobeExplorer`, as the model overlay does. Work in the ECEF frame, include the log-depth chunks, and choose a `renderOrder`. A layer that needs the explorer's own state, as the ice and sea level layer needs the timeline's years, keeps its state in `useGlobeExplorer` and is rendered by `GlobeExplorer` beside `sceneLayers`. A coarse class raster can reuse `createModelOverlayMaterial`, which culls back faces instead of testing depth and so needs no depth chunks.

**An external link.** Links in cards go through `components/SafeLink.tsx`, which allows only the https hosts listed in `lib/externalHref.ts`. A new source needs its host added there.

**A reading or a follow entry.** Both site cards (the globe's site card and the Sources tab of the Anatolia site panel) show a "Reading list" and a "Follow this site" section when the site has entries; `components/SiteReading.tsx` draws them. A reading entry goes in `lib/reading/readingLists.ts`: authors, year, title, where it was published, a kind (excavation report, peer-reviewed paper or popular book), one level line on what the work is, and an https address if there is one. List the excavators' publications and the main books arguing other readings side by side, and describe each without judging it. A follow entry goes in `lib/reading/followLinks.ts`: a name, what it is, a kind (project page, feed or account), an https address, and the sites it belongs to, or `WHOLE_ATLAS`. The About panel lists every follow entry. A site's ids (its curated id and its world-catalogue ids) are named once in `lib/reading/siteIds.ts`, so an entry is found from either card. Only ids of that same place belong there. Pleiades 961911 is a different place with a similar name, and it is not one of Göbekli Tepe's ids. Confirm a citation against a library or publisher record before adding it, and open an address before linking it. A new host goes in `lib/externalHref.ts`.

**A news item.** The Story tab of an Anatolia site panel, the catalogue place panel, and the globe site card show a "News" section when that site has items. `components/SiteNews.tsx` draws them newest first, with the date, the status word (`reported`, `disputed`, `rumour-denied`) and the source link. A site with none shows nothing. An item is one object in `lib/news/siteNews.ts`; how to append one is in [`Anatolia/atlas/lib/news/README.md`](../Anatolia/atlas/lib/news/README.md). The date is the day the source gives. The summary says what that source reports, and the item does not change the site's published record. A new source host goes in `lib/externalHref.ts`. On the globe, a report from the last 90 days marks each catalogue site it names (`lib/news/recentNews.ts`). The legend lists those sites, quoting each headline with its source, and flying to one opens that site's card. Hooks: `[data-role='globe-explorer']` carries `data-news-pins` (`on` or `off`), `[data-role='news-pins']` is the switch (the legend's, and the settings panel's while that panel is open), `[data-role='news-pin-list']`, `[data-action='show-news-site'][data-site]`, and `[data-role='news-site-ring'][data-site]`.

**A new data source.** That is a catalogue change. See [`world-catalogue.md`](world-catalogue.md).

### Browser checks

`check_detail_coverage.mjs`, `check_panel_flight.mjs` and `check_timeline_keys.mjs` drive the Anatolia atlas in headless Chrome with puppeteer-core, against the dev server at `http://127.0.0.1:43127/`. They launch `/usr/bin/google-chrome-stable`, and one writes under `/tmp`. So they run on Linux as written. The first page of the app is now the globe, and these scripts have not been re-run for this document.

On Windows, run the rest of the suite without them:

```bash
pytest --deselect tests/test_detail_coverage.py --deselect tests/test_panel_flight.py::test_rapid_clicks_escape_and_midflight_close --deselect tests/test_timeline_keys.py
```

For a browser check of your own on Windows, puppeteer-core works with the installed Chrome and software WebGL. This was run against the dev server for this document:

```js
import puppeteer from "puppeteer-core";

const browser = await puppeteer.launch({
  executablePath: "C:/Program Files/Google/Chrome/Application/chrome.exe",
  headless: true,
  args: ["--use-gl=angle", "--use-angle=swiftshader", "--enable-unsafe-swiftshader", "--window-size=1280,800"],
});
const page = await browser.newPage();
await page.goto("http://127.0.0.1:43127/?view=globe", { waitUntil: "domcontentloaded" });
await page.waitForSelector("[data-role='site-status']", { timeout: 60000 });
console.log(await page.$eval("main", (main) => main.dataset.worldView));
await browser.close();
```

Save it inside `Anatolia/atlas` so Node finds puppeteer-core, and run it with `node`. Software rendering is slow: allow a minute or more for the globe to settle. Do not wait for `networkidle0`, because the globe keeps streaming tiles. Useful hooks are the `data-*` attributes: `main[data-world-view]`, `[data-view='globe']`, `[data-role='site-status']`, `[data-role='globe-look']`, `[data-action='view-terrain']`, `[data-action='walk-site']` on the atlas site panel and on a globe site card that offers a walk, `[data-action='walk-offer']` on the zoom prompt, and `[data-place-state]` on the place view (`loading`, `ready`, `error`). Look at a screenshot before trusting a pass.
